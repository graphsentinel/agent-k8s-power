Shrinking an agent's Kubernetes power

A coding agent asked to read one ConfigMap usually holds a credential that can do everything its ServiceAccount, or the human who delegated to it, can do. This lab measures two mechanisms that narrow it, constrained impersonation as released and a prototype of token constraints as proposed, against the same task and the same attacks.

The problem

KEP-5917's motivation says it directly:

delegating an action to an agent today requires that a user trusts the agent (or the MCP server) to have the same level of access to the cluster as they do.

Two mechanisms can narrow that power, in different places:

KEP-5284 · constrained impersonation

beta since v1.36, on by default. The limit lives in RBAC objects on the impersonator (impersonate-on:<mode>:<verb>), set by whoever can write RBAC.

KEP-5917 · authenticator-provided constraints

proposed in PR #5918. The limit lives in the token: the authenticator puts constraints into the user's extra fields and a first-in-chain authorizer denies what they do not allow. Per token, so per task.

The lab asks, for one agent task: which attacks does each mechanism stop, where does each fall back to the wider power, and does kubectl auth can-i tell the agent the truth?

Not a claim that Kubernetes RBAC is insecure (the baseline is wide by configuration), not a statement about KEP-5917's final behaviour (M2 and M3 are our prototype of the proposal's text), and not a vulnerability report.

Where they differ

  1. M1 widens through RBAC around it. With the legacy impersonate role also bound, every forbidden action is allowed. A verbs: ["*"] rule in the task Role allows direct LIST and PATCH without impersonation, and a later view RoleBinding allows direct reads: the M1 limit is not on the credential.
  2. M2's outcome depends on how the PR text is read. With a name-restricted rule, LIST across all namespaces is allowed under one reading and denied under a stricter one; a malformed constraint gives the agent's full RBAC unless parsing fails closed; a constraint that allows impersonation lets the impersonated identity read the Secret unless impersonation fails hard.
  3. The constraint reaches an aggregated API. metrics-server's delegated SubjectAccessReview carried it (team-a allowed, team-b denied).
  4. can-i drifts. Under M1, SelfSubjectAccessReview reported the task as not allowed while it was, and a Secret as allowed while it was denied; under M2, SelfSubjectRulesReview reported the Secret as readable while the webhook denied it.
  5. Revocation does not reach open watches. In M0, M1 and M2, a watch opened while it was allowed kept receiving events after the permission was removed or the 60 s token expired, while new requests were refused. This is the documented design: authorization happens when a request starts.

Scope: k3s v1.37.1 with the RBAC objects in the repository, Keycloak 26.8.0, and our prototype of the KEP-5917 text at a346858. The results say nothing about a future implementation of KEP-5917.

Run it yourself

On Ubuntu 24.04 or 26.04 (4+ CPUs, 8 GB RAM, 20 GB disk). Tools that are already installed are left as they are; Docker and Python come from Ubuntu's own packages.

git clone https://github.com/graphsentinel/agent-k8s-power.git && cd agent-k8s-power
scripts/platform.sh install      # Docker, python3, openssl; kubectl and k3d only if missing
scripts/platform.sh cluster-up   # lab CA, kube-apiserver configuration, k3d cluster
scripts/lab.sh all               # install the lab, run the plan, compare with the reference

On a fresh 8-CPU VM one pass of the plan took about 10 minutes and five passes about 35, each ending with ALL CHECKS PASSED. The lab can be removed and reinstalled without touching the cluster (scripts/lab.sh reinstall). Details are in the README.
